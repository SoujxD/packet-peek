# Benchmark record — 2026-10-28

These are maximum-speed replay measurements on an isolated Docker/WSL2 veth pair, not physical-NIC wire-speed or maximum engine capacity measurements. The replay generator achieved roughly 100 Mbps. It did not saturate the engine, so these results establish no speed advantage for either filter placement.

The downloaded capture is not committed. Each trial replays it ten times: 511,830 packets, 201,517,590 Ethernet bytes. Filter `tcp port 80` selects 9,519 parsed packets per pass (95,190 per trial), forming 1,374 directional flows. Other traffic is deliberately present to exercise filter placement. Some userspace trials also received two IPv6 control packets generated by the private veth link.

## Exact workload and metric

Engine commands, executed in `/work`:

```sh
/work/build/benchmark-native/libpeek --interface peek-rx --filter 'tcp port 80' --idle-seconds 30
/work/build/benchmark-native/libpeek --interface peek-rx --filter 'tcp port 80' --idle-seconds 30 --userspace-filter
tcpreplay --intf1=peek-tx --topspeed --loop=10 build/benchmarks/bigFlows.prefix.pcap
```

Stdout protobuf output was sent to `/dev/null`; .NET, database, and UI are excluded. The harness starts capture 0.5 seconds before replay, waits two seconds for drainage afterward, then sends SIGINT. Both veth endpoints are inside a container with `--network none`; no traffic is sent to the host's real network.

`parsed_packets_per_second = packets / read_span_seconds`, rounded to two decimal places. Read span is monotonic time between first and last captured packet reads, including any processing/waiting between them. It excludes setup and final idle drainage. It is observed matching traffic throughput, not a saturated capacity claim. Capture counts are libpcap `ps_recv`; drops are `ps_drop`, not an end-to-end proof of every possible loss mechanism.

## Reproduce

Requires Docker on a Linux-capable host. Run from the repository root in Bash. The tool container is task-local; its `NET_ADMIN` capability is used only in a separate network-isolated trial container.

```sh
docker run -d --name packetpeek-native -v "$PWD:/work" -w /work ubuntu:24.04 sleep infinity
docker exec packetpeek-native sh -c 'apt-get update && apt-get install -y --no-install-recommends build-essential cmake pkg-config libcriterion-dev libpcap-dev protobuf-c-compiler libprotobuf-c-dev python3 python3-protobuf protobuf-compiler tcpreplay iproute2 curl ca-certificates'
docker exec packetpeek-native sh -c 'mkdir -p build/benchmarks && curl -fL --range 0-20971519 --max-filesize 52428800 https://s3.amazonaws.com/tcpreplay-pcap-files/bigFlows.pcap -o build/benchmarks/bigFlows.prefix.raw && python3 tests/benchmarks/prepare.py build/benchmarks/bigFlows.prefix.raw build/benchmarks/bigFlows.prefix.pcap && cmake -S c -B build/benchmark-native -DBUILD_TESTING=OFF -DCMAKE_BUILD_TYPE=Release && cmake --build build/benchmark-native'
docker commit packetpeek-native packetpeek-native-tools:local
docker run --rm --network none --cap-add NET_ADMIN --cap-add NET_RAW -v "$PWD:/work" -w /work packetpeek-native-tools:local python3 tests/benchmarks/run.py build/benchmark-native/libpeek build/benchmarks/bigFlows.prefix.pcap build/benchmarks/results
docker rm -f packetpeek-native
```

The source checksum is the reproducibility check; upstream packages and floating base tags can change. For a physical-NIC benchmark, use a dedicated sender and receiver, specify link speed, measure sender and receiver drops, and increase offered load until the receiver saturates. Those measurements have not been performed here.
